# Telegram: подробный разбор

## Почему Telegram — особый случай

Для web-сервисов доменный каталог покрывает имена, которые клиент разрешает
через управляемый DNS. Это не гарантия для клиентов с собственным DNS,
закэшированными IP или прямыми IP-соединениями.

Telegram устроен иначе. Помимо DNS-резолвимых доменов, клиенты Telegram:

- подключаются напрямую к IP-адресам из собственных подсетей (AS62041, AS62014)
- получают список IP дата-центров при первом подключении и кэшируют его
- используют MTProto-протокол, который DPI может распознавать и замедлять

Поэтому для Telegram используется **три уровня маршрутизации**:

1. **Домены** — покрывают web-интерфейс, CDN, API, экосистемные сервисы
2. **Официальные подсети** — IP-диапазоны дата-центров Telegram
3. **AS62041 peering / CDN** — подсети, используемые для медиа-доставки в России

## Проблема DPI-троттлинга в России

Одна из возможных причин — DPI (Deep Packet Inspection), который распознаёт
Telegram-трафик на уровне протокола. Возможные симптомы:

- Текстовые сообщения отправляются нормально
- Фото и видео грузятся десятками минут или не грузятся вовсе
- Проблема непостоянна — зависит от провайдера, региона и времени суток

Подробное обсуждение проблемы: [Flowseal/zapret-discord-youtube#5820](https://github.com/Flowseal/zapret-discord-youtube/issues/5820)

Эти симптомы также возможны при сбоях клиента, CDN, прокси или домашнего
канала. Само зависание медиа не доказывает DPI или пропущенный домен.

Актуальный список всегда доступен по адресу: https://core.telegram.org/resources/cidr.txt

### AS62041 peering / CDN

Эти подсети не входят в официальный `cidr.txt`, но анонсируются через автономную систему Telegram (AS62041) и используются как CDN/пиринг для доставки медиа:

```
5.28.192.0/18
95.161.64.0/19
```

**Про 95.161.64.0/19:**

Формально диапазон принадлежит компании Global Network Management (GlobalNet), но фактически анонсируется через AS62041 (Telegram). В официальном `cidr.txt` отсутствует.

Зачем он нужен: сеть используется Telegram как CDN и точки пиринга для ускорения доставки контента (фото, видео) в российском регионе. Без неё Telegram будет работать, но медиафайлы могут грузиться значительно медленнее — или не грузиться вовсе при жёстких блокировках.

Wireshark-анализ живого трафика показывает `/19` (шире, чем рекомендуемый `/20`). Используем `/19` для полноты покрытия.

**Про 5.28.192.0/18:**

Укрупнённый диапазон используется несколькими публичными Telegram rule lists
(`itdoginfo/allow-domains`, `Loyalsoldier`, `blackmatrix7`) и покрывает ранее
зафиксированные `5.28.192.0/21` и `5.28.248.0/21`. Это всё ещё Telegram
AS/peering coverage, а не shared CDN-провайдеры.

### Legacy / observed

```
91.108.36.0/22
109.239.140.0/24
```

Эти дополнительные сети сохранены для совместимости; они не входят в
официальный `cidr.txt` на дату сверки. Удалять наблюдавшуюся сеть только из-за
её отсутствия в этом файле нельзя: CDN/DC могут выдавать адреса отдельно.

## Почему shared CDN IP не роутим статически

При Wireshark-анализе видно, что часть web-трафика Telegram проходит через shared CDN-провайдеров (Cloudflare, Google, Fastly). Эти IP-адреса задокументированы в `configs/static-networks.txt` как справочная информация, но **не добавлены как статические маршруты**.

Причина: это общая CDN-инфраструктура. Добавление, например, `172.67.132.10/32` в статические маршруты отправит через VPN весь трафик к этому IP — включая другие сервисы, не связанные с Telegram. Telegram web-трафик к CDN уже покрыт доменным роутингом (`telegram.org`, `t.me` и т.д.).

## IPv6

IPv6-подсети Telegram задокументированы в `static-networks.txt` как закомментированные записи:

```
# 2001:67c:4e8::/48
# 2001:b28:f23c::/48
# 2001:b28:f23d::/48
# 2001:b28:f23f::/48
# 2a0a:f280::/32
```

Текущий supported mode в проекте: **IPv6 disabled**.

Важно:

- одного “раскомментировать несколько блоков” недостаточно
- включение IPv6 только в Merlin UI без полноценного managed IPv6-path создаёт риск bypass мимо repo-managed split-routing
- generic IPv6 residue в Merlin / `ip6tables` / `AllowedIPs = ::/0` сам по себе не означает, что dual-stack routing уже готов

Dual-stack здесь рассматривается только как **отдельный будущий проект**, и стартовать его имеет смысл только после одновременного выполнения условий:

1. В Merlin реально включён IPv6
2. На LAN есть live IPv6 runtime
3. Реализованы и проверены IPv6-классификация, перехват, DNS и Reality-egress
4. Проверены отсутствие bypass и восстановление после перезагрузки

Legacy WireGuard остаётся cold fallback и не является основой будущего
dual-stack.

## Почему обновления доменов может быть недостаточно

Telegram выдаёт клиенту `dc_options` с IP, портом и признаками `media_only`,
`cdn` и `this_port_only`. Адреса могут меняться в зависимости от нагрузки и
местоположения клиента. Файлы могут находиться в другом DC или возвращать
`upload.fileCdnRedirect` на отдельный CDN DC. См. официальные описания
[DC selection](https://core.telegram.org/api/datacenter) и
[encrypted CDNs](https://core.telegram.org/cdn).

Поэтому надо различать четыре проверки:

| Проверка | Что подтверждает | Что остаётся непроверенным |
|---|---|---|
| HTTP к `telegram.org` | Доступность web-сайта через выбранный выход | MTProto, загрузка файлов, звонки |
| MTProto `req_pq_multi -> resPQ` с проверкой nonce | Двусторонний обмен протокола с конкретным DC | Авторизованная сессия и выбранный клиентом media/CDN DC |
| Загрузка публичного web-медиа | Проверенный HTTPS CDN-host и объект | Передача файлов нативного клиента по MTProto |
| Воспроизведение зависания на устройстве | Фактический клиентский путь в момент сбоя | Другие устройства, сети и сценарии |

SOCKS-проба с роутера проверяет upstream, но сама по себе не проверяет
LAN `PREROUTING/REDIRECT`, первый hop удалённого клиента или его собственные
proxy-настройки. Эти части проверяются отдельно по живым правилам и событиям.

Обычный Channel A LAN split перехватывает managed TCP, а managed UDP/443
блокирует для TCP fallback. Это правило не делает весь UDP-трафик Telegram
управляемым. Звонки используют отдельные параметры соединений, включая
[WebRTC STUN/TURN](https://core.telegram.org/constructor/phoneConnectionWebrtc),
и требуют отдельного воспроизведения. Нельзя приравнивать UDP/443 drop к
проверке всех звонков или исправлять их добавлением случайных доменов.

## Диагностика периодических зависаний

1. Зафиксировать время, устройство, версию Telegram, домашний Wi-Fi или
   выбранный удалённый канал; различать «Connecting», сообщения, медиа и звонки.
2. Сверить `configs/static-networks.txt` с live-файлом
   `/jffs/configs/router_configuration.static_nets`, `VPN_STATIC_NETS` и
   `/opt/etc/sing-box/rule-sets/stealth-static.json`. Для доменов проверить
   dnsmasq-каталог, managed DNS и `stealth-domains.json`.
3. Сопоставить время сбоя с sing-box, conntrack, загрузкой CPU, доступной RAM,
   заполнением conntrack и перезапусками служб. Сохранить исходные данные
   только в gitignored operator reports; не публиковать адреса клиентов.
   Для удалённого Channel A отдельно проверить счётчик ingress `connlimit`:
   лимит применяется к source IP, который несколько устройств могут разделять
   за NAT. Важен прирост DROP во время зависания, а не накопленное значение.
   Сопоставить его с количеством одновременных соединений этого source;
   общий свободный conntrack сам по себе не исключает срабатывание лимита.
4. Проверить web и MTProto отдельно. Повторять короткие пробы в ограниченном
   временном окне; успешная серия не исключает сбой позднее или на другом DC.
5. Для неудачного соединения определить IP/порт и фактический outbound.
   Добавлять только подтверждённый адрес/префикс Telegram, когда обнаружен
   пропуск; не добавлять целиком shared CDN, ASN или `91.108.0.0/16` по одному
   чужому rule list.
6. Если маршрут верен, сравнить тот же сценарий через другой backend
   контролируемой пробой. Не переключать общий production-egress ради
   диагностики одного приложения и не менять sensitive-sites mode.

Текущий `egress-backend-health` содержит HTTP-canary Telegram, а не MTProto
или авторизованную загрузку медиа. Его `OK` нельзя использовать как
единственное доказательство исправления. Runtime-версии и release notes
проверяются отдельно: найденный upstream issue должен совпасть по платформе,
версии и transport перед обновлением.

Для iPhone / Shadowrocket сравнение каналов выполняется с одним и тем же
клиентским Config: сначала проверить, что соединение к Telegram действительно
выбрало `PROXY`, затем сопоставить его с router inbound и outbound. Общие
GeoIP/DIRECT-правила или встроенный Telegram proxy могут изменить путь ещё до
роутера. Готовый строгий proof Config и daily-template описаны в
[client profile guide](../../client-profile-factory/docs/client-profiles.md#shadowrocket-proof-config-for-channels-abc).
Переключение серверов A/B/C не заменяет эту проверку; QR и credentials ради
диагностики не регенерируются.

## Как обновлять подсети

1. Скачайте актуальный список: `curl -s https://core.telegram.org/resources/cidr.txt`
2. Сравните с секцией «Официальные» в `configs/static-networks.txt`
3. Дополнительно сверить наблюдаемый адрес с BGP и текущим клиентским DC/CDN;
   отсутствие в официальном файле не означает автоматически чужую сеть
4. При подтверждённом пропуске обновить каталог, проверить managed-policy и
   split-parity tests, затем выполнить разрешённый deploy и live-проверку

Для BGP-анализа можно использовать:
- https://bgp.he.net/AS62041 — маршруты AS62041 (Telegram)
- https://bgp.he.net/AS62014 — маршруты AS62014 (Telegram)
- [RIPEstat announced-prefixes](https://stat.ripe.net/docs/data-api/api-endpoints/announced-prefixes)
  — первичные RIS-наблюдения; учитывать `query_endtime`, окно наблюдения и
  минимальную видимость. Результат не гарантирует покрытие всех внешних CDN.
