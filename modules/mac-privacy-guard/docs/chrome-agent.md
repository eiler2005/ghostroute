# Chrome agent: управление из приложения

## Возможности и порядок работы

В приложении **Google Chrome** показывает подключённые сеансы расширения.
Идентификатор временный, создаётся при запуске worker; это не имя пользователя,
не отпечаток профиля и не доказательство защиты всех профилей Chrome.
Переключатель передачи решений правил относится к текущему сеансу worker; новый
сеанс начинает с включённой передачей и блокировкой чувствительного каталога.
Главные кнопки доступны и на экране «Обзор»; HTTP-диагностика не нужна для их работы.

| Действие приложения | Что делает Chrome | Что остаётся независимым |
|---|---|---|
| Передавать разрешения и блокировки | Включает/выключает отправку DNR matches в общий журнал | Сам блокировщик и локальные счётчики продолжают работать |
| Открыть доступ в Chrome | Добавляет отзывное session allow rule для того же каталога, пока приложение на связи | Статический ruleset включён; proxy/VPN/маршрут не меняются |
| Закрыть доступ в Chrome | Удаляет allow rule и возвращает блокировку новых запросов | Доступ отдельного браузера Guard не меняется |
| Начать / остановить диагностику | Управляет только подготовленной панелью DevTools, до 60 секунд | Не открывает доступ и не снимает блокировку |
| Очистить | Стирает HTTP-метаданные, ссылки на ответы и предпросмотр | Общий журнал блокировок очищается отдельно |
| Показать текст | Запрашивает один небольшой текстовый ответ | Не запрашивает заголовки, cookies или тело запроса |

**Открытие доступа сохраняет текущую сеть и proxy обычного Chrome.** Проверка
IP/страны и включение стороннего VPN этим действием не выполняются. Уже
заблокированную страницу нужно обновить в той же вкладке. Дополнительный
защищённый браузер запускается отдельно и не нужен для управления блокировкой.
Ограничения в одну минуту нет: ответы приложения продлевают lease на 15 секунд.
Обнаружение отсутствия приложения, истечение lease и запуск worker удаляют правило;
новый запуск браузера очищает session rules. Эти действия зависят от планирования
Chrome, включая сон/возврат: это не системный kill switch. Для постоянного ручного
отключения расширения используется Chrome; выключенное расширение не принимает
команду обратного включения.

Восстановление DNR-блокировки действует на новые запросы и не обрывает уже
открытые WebSocket/streaming-ответы. Для прекращения таких потоков закрыть
соответствующую вкладку. Это граница блокировки новых запросов через DNR.

## Счётчики и журнал

`onRuleMatchedDebug` учитывает только наши static deny и session allow rules.
Число на иконке — сумма разрешённых и заблокированных запросов каталога за сеанс
worker, popup показывает обе части. В приложении — доставленные решения за запуск
engine; выключенная передача, потери и независимые перезапуски объясняют различия.
Это не TCP-соединения, объём трафика или HTTP-успех. Allow фиксируется до ответа
сайта: чужой блокировщик, proxy или сеть ещё могут отказать. Для этих событий
нет измеренных байтов/длительности; UI показывает «—». Сайты вне каталога не
записываются. Поля `allowed` / `connections` API сохраняют смысл туннелей шлюза;
обычные запросы учитываются в отдельных `chrome_allowed` / `chrome_blocked`.

Для долгой загрузки использовать явно подготовленную HTTP-диагностику ниже.
Она показывает статус и время завершённых ответов; одно событие allow не
определяет, где задержка: DNS/TLS, текущий VPN/proxy, сервер или код страницы.

## Подготовка HTTP-просмотра

1. В нужной обычной вкладке открыть DevTools: **⌘⌥I → Guard**.
2. Включить «Разрешить управление этой вкладкой из приложения Guard».
3. В приложении выбрать её сеанс Chrome и нажать «Начать на 60 секунд».
4. Выполнить действие на странице или перезагрузить её. HTTP-таблица показывает
   домен, метод, статус, MIME и время ответа. Блокируемый запрос может не дать
   обычного завершённого HTTP-ответа; его отказ смотрят в общем журнале.
5. Выбрать строку и явно запросить текст ответа, если он нужен.
6. «Остановить и стереть» сразу закрывает приём данных в приложении и отправляет
   остановку панели. Скрытие панели отзывает разрешение; истечение сеанса очищает
   данные. Навигация стирает предыдущие ответы, запись той же вкладки продолжается.

Одновременно подготовлена одна панель на worker. Подготовка другой отзывает
предыдущую. Другие вкладки фоном не читаются. В защищённом Chrome расширения
выключены; там используется встроенный **Network → Response**, без установки
блокировщика обычного профиля.

## Данные и доверие

Панель использует `chrome.devtools.network.onRequestFinished` и `getContent`:
ответ уже расшифрован самим браузером. Корневой сертификат перехвата не нужен.
Manifest добавляет `devtools_page`, но не добавляет разрешения `debugger`,
`webRequest`, `tabs`, cookies, proxy, host permissions или content scripts.

Метаданные: максимум 100 записей в отдельной памяти engine/панели. В общий
журнал из них ничего не копируется. HAR/полные URL/параметры/headers не пересылаются.
Для ответа сохраняется ограниченный reader и непрозрачный случайный идентификатор.
Текст читается только по отдельному действию; допускаются текстовые MIME с
известным размером до 256 KiB, отображается максимум 1024 символа. Binary/base64,
слишком большие и уже удалённые ответы не показываются. HTML отображается инертно.
Не обещать очистку личных данных внутри текста: он может содержать secrets/PII.

API выдаёт один предпросмотр со сроком 15 секунд; Stop, смена/скрытие
подготовленной панели, истечение capture и «Скрыть текст» стирают его раньше.
Полный текст и previews не попадают в event journal, отчёты, telemetry, Git или
дисковую очередь. Истечение проверяется на очередном сообщении или запросе API;
обновление экрана и сон могут отложить фактическое удаление из UI/памяти. Это
логическое удаление из state, не гарантия криминалистического обнуления RAM.
Chrome ведёт собственную историю/DevTools log независимо.

Приложение обращается к token-authenticated loopback API. Native host разрешён
только установленному ID расширения и общается через пользовательский Unix
socket. Входные JSON-схемы строгие, кадр ограничен 8192 байтами. Chrome не получает
токен API, credentials proxy и право квалифицировать маршрут.

Команды: только `start`, `stop`, `clear`, `preview`, `reporting_on/off`,
`allow_sites`, `block_sites` (старые `pause_protection` / `resume_protection`
сохранены для совместимости); одна ожидающая команда на профиль,
случайный ID, срок доставки 5 секунд, явный result. Поздние/чужие previews и
неподготовленные сеансы отклоняются. Агент сообщает состояние примерно каждые
0,5 секунды; сеанс без сигнала старше 6 секунд удаляется вместе с разрешением доступа.
Всего сохраняется до 8 агентов. Не расширять канал до произвольных CDP/JS/URL
команд, автоматизации других вкладок или управления system proxy.

После нажатия основной кнопки GUI до 1,5 секунды опрашивает только небольшой
Chrome snapshot каждые 100 мс, завершая ожидание после фактического применения
и acknowledgement. Полный журнал сохраняет обычный интервал 1,5 секунды.
Браузерный тест делает 16 переключений в обе стороны и проверяет бюджет менее
двух секунд на каждое. Это цель для работающих процессов, не гарантия времени
при зависании Chrome/OS, сне или потере IPC; UI не выдаёт desired state за actual.

## Проверки

```bash
./modules/mac-privacy-guard/tests/run.sh
node modules/mac-privacy-guard/tests/diagnostics.mjs
swift run --package-path modules/mac-privacy-guard/native GuardNativeChecks
node modules/mac-privacy-guard/tests/browser.mjs
```

Реальный изолированный Chromium доказывает открытие/закрытие доступа в той же
вкладке при закрытом дополнительном шлюзе, продление разрешения дольше минуты,
независимое reporting и восстановление после потери engine. Контракт DevTools callbacks проверен
через настоящий extension runtime → Native Messaging → engine → команды обратно,
включая solicited preview и очистку. Отдельные frontend fixtures проверяют inert
HTML. Подмена callback в тесте не является приёмкой настоящего контейнера DevTools:
его открытие/видимость/вкладку Guard дополнительно проверять на установленном Chrome.
