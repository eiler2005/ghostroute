# Надёжность соединений и диагностика ошибок Chrome

Этот документ разделяет действующее поведение Guard и план дальнейших улучшений.
Реальные назначения, внешний PAC и сетевые журналы остаются в приватных
операторских материалах. Примеры ниже не описывают конкретное развёртывание.

## Что защищено сейчас

| Назначение | Как выбирается путь | Что происходит при отказе |
|---|---|---|
| Чувствительный каталог | Обязательный gate Guard и проверенный домашний HTTPS-маршрут | Доступ закрывается; прямого запасного пути нет |
| Обычный сайт, основной режим `network` | Текущая сеть Mac; дома — существующие managed/direct правила роутера | Продолжает работать при паузе/отказе Guard; сбой сети или сайта остаётся обычной сетевой ошибкой |
| Обычный сайт, явно выбранный `external_pac` | Снимок внешнего PAC с проверенными локальными исключениями | Применяются исходные правила PAC; Guard не добавляет DIRECT после ошибки |

Основной режим больше не зависит от внешнего браузерного proxy и не требует
исключения для каждого сломанного обычного сайта. Старый embedded PAC удаляется
при применении `network`. Это заранее выбранный путь, а не автоматический обход
после ошибки. Внешний proxy остаётся зависимостью только режима совместимости.
Успех canary Guard подтверждает его проверяемый маршрут и не доказывает
доступность каждого сайта через внешний proxy. Селективная защита также не
покрывает все ресурсы вкладки: неизвестные зависимости могут идти вне каталога.

## Как отличить причины

| Наблюдение | Что оно означает | Следующий шаг |
|---|---|---|
| `ERR_BLOCKED_BY_CLIENT` | Запрос остановлен правилом расширения; это может быть Guard или другой блокировщик | Сверить профиль, статус Guard и журнал решения; после разрешения обновить вкладку |
| `ERR_TUNNEL_CONNECTION_FAILED` | Chrome не смог создать proxy-туннель; код сам по себе не называет виновный proxy и его причину | Проверить выбранный путь и локальный NetLog |
| В NetLog выбран внешний proxy и на CONNECT получен HTTP 503 | Proxy отказал до установления HTTPS-туннеля к сайту | Проверять доступность/правила этого пути; очистка cookies не устраняет такой отказ |
| HTTP 503 после успешного CONNECT и TLS | Ответ пришёл уже на уровне HTTPS-запроса | Проверять сайт и его зависимости; не приписывать этот статус CONNECT-proxy |
| В Incognito работает | Профили отличаются настройками расширений, proxy и данными сайта | Использовать как подсказку, затем подтвердить причину; это не проверка защиты |

Ответ 503 на CONNECT не раскрывает внутреннюю причину отказа внешнего proxy.
Без его диагностики перегрузка, недоступность назначения и политика провайдера
остаются гипотезами. Это повторяемый класс сбоев зависимости, а не доказательство
поломки роутера или macOS.

## Порядок проверки

1. Записать локально точный код ошибки, профиль Chrome, версию расширения и
   статус маршрута. Проверить, входит ли назначение в sensitive-каталог.
2. Сверить состояние приложения и popup. Зелёный подтверждённый статус относится
   к пути Guard. Разрешение DNR и рост счётчика не подтверждают HTTP-ответ сайта.
3. Для завершённых HTTP-ответов использовать [диагностику подготовленной вкладки](user-guide.md#если-сайт-долго-загружается).
   Если сбой произошёл до HTTPS-туннеля, её данных может быть недостаточно.
4. При необходимости открыть `chrome://net-export`, оставить режим удаления
   приватных данных, начать короткую запись, воспроизвести один отказ и остановить
   запись. Проверить выбранный proxy, CONNECT-ответ и сетевой код ошибки.
   Даже такой NetLog может раскрывать адреса и служебные данные: хранить только
   локально в игнорируемом приватном каталоге, не включать в Git или обычный backup.
5. После исправления обновить расширение, дождаться подтверждения маршрута и
   заново открыть исходную страницу в том же обычном профиле. Не повторять
   автоматически отправку формы, оплату или другое действие с неизвестным итогом.

Сетевой отказ обычного сайта вне каталога сейчас может отсутствовать в журнале
Guard: расширение не наблюдает весь трафик Chrome и не расшифровывает HTTPS.
Встроенного автоматического объяснения всех proxy-ошибок пока нет.

## Что решает точечное исключение

В основном режиме исключения не нужны. Следующий механизм сохранён для
необязательного `external_pac` и отката его приватной конфигурации.

[Приватное ordinary-исключение](operations.md#проверенные-исключения-обычных-сайтов)
устраняет зависимость выбранного обычного домена и его поддоменов от внешнего
proxy. Оно использует текущую сеть Mac; страна выхода не подтверждается.
Пересечение с sensitive-каталогом запрещено. Успешная реальная вкладка подтверждает
исправление этого пути, но не гарантирует работу других сайтов или самого proxy.

Installer сохраняет исходный `ordinary-direct-domains.txt` и заново собирает
локальную политику. При восстановлении на другой Mac нужен этот приватный файл
из зашифрованной копии. После изменения требуются пересборка extension и Reload;
наличие новых файлов на диске не подтверждает активацию в Chrome.

## План улучшений

Следующие пункты предлагаются к реализации; они не являются возможностями
текущей версии и требуют отдельной приёмки маршрутов.

| Приоритет | Изменение | Практическая ценность и граница |
|---|---|---|
| P1 | Понятная диагностика в приложении: домен, выбранный путь, этап ошибки, время последней проверки и безопасное действие | Убирает необходимость угадывать по общему сообщению Chrome. Нужен отдельный источник сетевых ошибок: текущие DNR-события не сообщают причину отказа CONNECT |
| P2 | Запасной путь для явно выбранных обычных сайтов и защита от частых переключений | Повторная ошибка может временно исключать отказавший путь. Переключение разрешается только политикой назначения; запросы с неизвестным результатом не переигрываются автоматически |
| P2 | Второй независимый проверенный путь для sensitive-каталога | Повышает доступность с сохранением требования к выходу. Нужны отдельные credentials, проверка TLS/egress и приёмка приложений; при отказе обоих путей доступ закрыт |

Явный базовый сетевой путь уже реализован и проверен. Следующее полезное
улучшение — диагностика P1; новые способы автоматического fallback не нужны
для исправления зависимости, удалённой в режиме `network`.
Автоматический переход на DIRECT после любой ошибки
может нарушить назначение выбранного proxy. Кроме того, он не исправляет отказы
самого сайта, авторизации или TLS. Внешняя страна/сервер в текущем PAC сохранены
снимком; смена у провайдера требует [повторного получения снимка](strict-mode.md#proxy-и-совместимость).

Возможность P2 зависит от поддерживаемого интерфейса провайдера и его авторизации.
Guard сейчас сохраняет PAC, а proxy authentication обслуживает внешнее расширение.
Перенос такого пути в собственный gateway не следует считать уже реализованным.

## Проверки и критерии приёмки

Текущие [проверки модуля](../tests/README.md) покрывают основной сетевой путь,
удаление старого embedded PAC, обычные сайты во время qualification/паузы/отказа
маршрута/потери engine и отсутствие прямого обхода sensitive gate. Отдельный
явный режим совместимости покрывает CONNECT 503 на fake proxy, отказ ordinary
site без нового DIRECT fallback и успех проверенного исключения. Unit-проверки
запрещают пересечения каталогов; browser fixture проверяет цвета состояний popup.

Для будущего переключения дополнительно нужны реальные сценарии: отказ proxy и
восстановление, потеря приложения, сон и смена сети, обновление правил провайдера,
отказ запасного пути и запрос с неизвестным результатом. Проверяются фактический
выход, отсутствие запрещённого DIRECT и повторной отправки действий, понятная
причина в UI и отсутствие циклических переключений. Canary и тестовая страница
не заменяют приёмку выбранных сервисов реальным клиентом.
