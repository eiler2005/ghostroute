# Routing Assurance Roadmap

> **RU primary.** This is the engineering register for routing security,
> recovery and evidence. The README presents implemented capabilities; this
> register records remaining work. Actual deployments, client results, backup
> locations and credentials belong in ignored private reports.

## English summary

The shared split, sensitive destination override, managed LAN guard, atomic
ipset snapshots, isolated channel ownership and reconnect-safe router deployment
are implemented. Their scope is defined in [privacy assurance](privacy-assurance.md).
The immediate work is to complete independent backup restore proof, authenticate
the Channel B home server on actual clients, and record end-to-end client
acceptance. Those are three different tasks; uploading an archive, starting a
listener or passing a router probe does not complete them.

P2 work covers full firewall/reboot recovery, a reproducible VPS image upgrade
path, safe catalog lifecycle and backup cadence. Additional hops, automatic
failover, blanket full-VPS routing and new lab transports remain conditional on
measured benefit. A roadmap entry does not authorize a runtime or profile change.
Two adjacent control-plane items also need triage: restoring reliable CI and
reviewing dependency-audit findings. They are tracked as RA-10/RA-11 below;
an audit severity count alone is not proof of production exploitability.

## Цель и критерий достаточности

Нужна предсказуемая и восстанавливаемая конфигурация с понятной границей защиты:

- Обычный direct-трафик после домашнего ingress выходит через home WAN.
- Managed-трафик использует выбранный VPS. Чувствительные совпадения при
  включённом режиме используют `sensitive-out -> hermes_vps` без автоматического
  fallback; Channel M сохраняет отдельный служебный home-WAN путь.
- Домашний ISP видит direct-направления и зашифрованное соединение с VPS.
  Внешняя сеть home-first клиента видит домашний ingress, если запрос действительно
  вошёл в этот канал. Клиентский DIRECT обходит эту модель.
- Сайт получает IP выхода и данные приложения. Учётная запись, cookies,
  fingerprint и разрешённая геолокация не исчезают после смены маршрута.

«Идеальная» схема не означает отсутствие всех рисков или внедрение всего backlog.
Достаточность проверяется наблюдаемыми результатами и восстановлением. Изменение
принимается, когда оно закрывает конкретный риск с меньшей операционной ценой,
чем сам риск. Нет доказанной пользы — нет изменения production.

### RA-01 — независимая копия и восстановление

В текущем приватном журнале отмечены загрузка зашифрованных объектов и проверка
скачанного manifest. Полная обратная проверка больших архивов остаётся открытой.
Адрес хранилища, имена объектов, даты и результаты ведутся только локально.

Порядок: скачать **весь** набор в отдельный каталог; сверить SHA-256;
аутентифицированно расшифровать и прочитать каждый архив; проверить наличие
Vault, настроек роутера, профилей и инструкции. Пароль не должен оказаться
единственной копией внутри этого же архива или только на исходном Mac.
Повторить по [backup runbook](../modules/secrets-management/docs/vault-offsite-backup.md).

Файловая проверка не равна восстановлению на запасном роутере. Последнее —
отдельный P2 drill при наличии оборудования, без перезаписи рабочего роутера.
Архив USB/JFFS/NVRAM не является образом прошивки или импортируемым ASUS CFG.

### RA-02 — аутентификация сервера Channel B

Генератор home-first B сейчас добавляет `allowInsecure=1`. При поддержке этого
параметра клиентом TLS шифрует соединение, но подлинность удалённого сертификата
не проверяется. Активный посредник, способный перенаправить соединение, может
принять туннель, узнать назначения и получить его VLESS-идентификатор.
Обычный пассивный наблюдатель не получает такой возможности только из-за этой
настройки. Внутренний HTTPS до сайта сохраняет собственную защиту при исправной
проверке сертификата приложением. См. [официальный TLS-контракт Xray](https://xtls.github.io/en/config/transports/tls.html).

Выбор решения зависит от реальных клиентских приложений: валидный сертификат
с проверкой имени либо поддерживаемое закрепление отпечатка. Локальная Mac-проба
с доверенно полученным отпечатком доказывает только эту пробу, а не настройку
ранее импортированного профиля телефона.

До изменения импортов составить приватный список клиентов, проверить поддержку,
описать параллельный переход и rollback. Требуется отдельное одобрение миграции
по [AGENTS.md](../AGENTS.md#client-profile-compatibility). Удаление одного флага
без подготовки сертификата/клиента может оборвать соединение. Общий deploy или
документационный commit не разрешает такую миграцию. Критерий включает как
положительную проверку, так и отказ при подставном сертификате в изолированном
тесте; production interception для проверки не требуется.

### RA-03 — приёмка на реальных устройствах

Для выбранного клиента записать приложение/версию, сеть и режим, затем проверить
direct, general managed и sensitive запросы, ожидаемый exit role, DNS, IPv6,
WebRTC где применимо и реальную передачу данных. Нужны как домашний LAN-клиент,
так и реально используемые внешние home-first клиенты. Методика и границы
доказательств — в [privacy assurance](privacy-assurance.md#evidence-levels).

- C1-Shadowrocket и native C — разные строки. Проверенный CONNECT не доказывает
  Naive; native C ждёт совместимого клиента.
- Неудачный доступ к D с одной Mac-сети не доказывает отказ на выбранном устройстве.
- Для Amn handshake не заменяет проверку DNS и приложений; AWG2 proof не доказывает
  AWG 3.1 или одновременную нагрузку всех настроенных peers.
- Для anyT сообщения/медиа и повторная приёмка после reboot уже подтверждены
  оператором. Это не подтверждает все восемь устройств под нагрузкой, звонки,
  roaming или DNS в режиме Config. Штатные DoH-запросы клиента не равны router
  port-53 override; это отдельная строка проверки.
- Для M нужны запросы API и медиа самого сервиса; живой SSH tunnel недостаточен.
- Для экспериментального Telegram sensitive-расширения нужны native сообщения,
  медиа, фоновое переподключение и смена сетей в согласованном окне наблюдения.

### RA-04–RA-06 — плановое укрепление эксплуатации

**Полный firewall/reboot drill.** Узкое повторное применение `firewall-start`
уже проверяет установку правил после вызова hook. Оно не моделирует предшествующий
интервал Merlin. Использовать независимый доступ и постоянные клиентские пробы;
сначала сохранить состояние и критерии остановки, затем провести одно
контролируемое событие. Не удалять глобальные цепочки ради демонстрации утечки.
У anyT уже есть отдельное подтверждение восстановления после реального reboot;
оно не закрывает измерение всего firmware-интервала для остальных каналов.

**VPS image.** В defaults и inventory остаётся `3x-ui:latest`. Зафиксировать
испытанный образ и процедуру обновления с совместимой копией БД/конфигурации.
Само закрепление digest не обеспечивает обновления безопасности: нужны review
новых версий и контролируемая замена. Не менять публичные ingress или клиентские
идентичности в рамках этой задачи.

**Каталог.** Текущий динамический ipset не имеет автоматического timeout.
Старые IP могут расширять охват, но безусловный TTL/flush способен отправить
ещё используемый managed IP напрямую. Сначала собрать данные, затем решать,
нужна ли очистка вообще. Чистота каталога не важнее сохранения нужного маршрута.

**Amn lifecycle (RA-09).** До продвижения lab устранить гонку «TUN появился,
но ещё не поднят» перед добавлением маршрута и сохранять первый LAN egress guard
после установки Amn-only FORWARD правил. Приёмка: задержанное поднятие TUN,
отказ запуска с полной очисткой owned state и повторный start без смещения LAN
guard. Эти изменения controller ещё не реализованы; текущая ручная эксплуатация
требует post-start health, а retry не заменяет устранение гонки.

### RA-10–RA-11 — проверки и зависимости контрольного контура

**CI.** В проверенном baseline установка Chromium остановилась из-за
несовместимости версии Playwright с образом `ubuntu-latest`; fast-набор отдельно
остановился на SSH preflight внутри ожидаемого fixture-сценария. Те же симптомы
есть до документационного изменения. Полный CI нельзя считать пройденным на
основании зелёных локальных проверок документации.

Закрепить поддерживаемый runner и проверить, что fixture-режим действительно
изолирован от operator SSH и live targets. Не выдавать CI доступ к реальному
роутеру, чтобы заставить fixture пройти; не отключать обязательные проверки.
Закрытие — весь обязательный workflow проходит на чистом checkout без приватной
инфраструктуры. См. [testing contract](testing.md).

**Зависимости Console.** Установка текущего lockfile выдаёт audit-сигналы высокой
и критической серьёзности. Это повод проверить конкретные advisories, а не
утверждать, что публичный сервис уже эксплуатируем. Разделить production и
dev-only зависимости, проверить достижимость затронутого поведения и выбрать
минимальное совместимое исправление. Сырые версии, advisory-вывод и результаты
проверки конкретного развёртывания хранить в приватном отчёте.

Не запускать безусловный `npm audit fix --force`. Изменения Next.js/React,
Playwright и публичной доставки требуют локальной seeded GUI-проверки desktop/
mobile и защищённого WebKit/iPhone контракта после deploy по AGENTS.md. Этот пункт
не разрешает менять channel ownership, DNS или firewall ради исправления UI.

### RA-12 — клиентская защита Mac

[Руководство пользователя](../modules/mac-privacy-guard/docs/user-guide.md) и
[матрица тестов](../modules/mac-privacy-guard/tests/README.md) описывают поставленный
контракт отдельно от deployment-specific приёмки.

[Mac Privacy Guard](../modules/mac-privacy-guard/README.md) реализован отдельным
модулем: native shell, fixed-proxy Chrome, allowlist для домашнего HTTPS CONNECT,
adapter с привязкой к VPN-интерфейсу, exit qualification и MV3 blocker.
Строгий Авто GhostRoute реализует mandatory PAC, qualified HTTPS transport,
изолированные gates агентов и Close/Resume для обычного Chrome; совместимый внешний
inline PAC сохраняется для остальных сайтов вместе с авторизацией его расширения.
Снимок не синхронизирует смену страны автоматически. Отдельный
защищённый браузер остаётся опцией. См. [контракт и границы](../modules/mac-privacy-guard/docs/strict-mode.md). Chrome-раздел управляет агентом и явно
подготовленной HTTP-диагностикой; response preview существует отдельно от журнала.
Локальные TLS/state/API fixtures и реальные Chrome проверки отказов отделены от
квалификации конкретного установленного VPN и его lifecycle.

Оставшаяся приёмка: включение blocker в фактически используемых обычных профилях
Chrome (включая Incognito при необходимости), измеренные sleep/network-change/
reboot сценарии и квалификация каждого выбранного стороннего VPN. Домашний
allowlist сверять с deployed sensitive policy после её изменения; один canary
не доказывает маршрутизацию всех доменов. Новый приватный профиль необходимо
явно включить в зашифрованную recovery-копию. Точный installed/activated/verified
статус остаётся в приватном отчёте. Не называть модуль системным firewall для
всех приложений и не снимать существующие сетевые ограничения ради его приёмки.
Проверять настоящую панель DevTools дополнительно к callback fixtures. Для
строгого режима отдельно принимаются proxy/privacy ownership, изменение сети и
зависимости сайтов: неизвестные CDN/IP/TURN TCP вне каталога остаются вне его
гарантии. Не расширять каталог автоматически ради зелёного статуса.

### RA-13 — Channel anyT: проверки обслуживания

`channel-anyt-check` автоматически включён в root `deploy.sh`, общую Ansible
задачу `deploy-gate.yml` и production update playbook anyT. Он сверяет локальный
approval manifest и live settings, проверяет enabled/process/source state,
cron/hooks, exact scoped INPUT и HTTPS через anyT с диагностической учётной
записью. Временный loopback клиент удаляется после успеха или ошибки. При
отсутствии server settings и наличии локального bundle проверка отказывает.

Реальный read-only запуск gate прошёл; fixture-тесты покрывают успешный запрос,
отсутствующий watcher/cron, ошибку firewall/HTTPS и cleanup. Это не проверка
всех восьми клиентов, внешнего ingress, каждого exit role или мобильной сети.
Playbooks, не использующие общий deploy gate, требуют явного вызова проверки.

Автоматического rollback shared deployment пока нет. Rescue anyT при неудачной
установке по-прежнему закрывает канал; восстановление предыдущей версии и
реальная клиентская приёмка остаются по
[maintenance checklist](../modules/routing-core/docs/channel-anytls-lab.md#maintenance-acceptance-checklist).
Watcher и минутный reconcile сохраняют прежние polling-границы.

### RA-14 — утверждённые артефакты и восстановление

Реализован `channel-anytls-profile --verify-approved BUNDLE`: полный обязательный
набор QR/URI/Config и исходных импортов сверяется по SHA-256, settings — по
canonical JSON hash. `--settings` дополнительно проверяет captured live settings.
Неполный/отсутствующий manifest, потерянный файл или несовпадение блокируют gate.
Production playbook выполняет проверку до первой мутации; `--export-eight` и
`--add-second` отказывают для утверждённого bundle до записи. Автоматического
переутверждения нет. Fixtures проверяют изменение каждого артефакта/settings,
неполную/отсутствующую approval и неизменность файлов при отказе экспорта.

Приватный manifest и сами файлы сохраняются в проверенной зашифрованной копии.
Сверка не защищает от сознательной замены и файлов, и доверенной approval записи;
удаление manifest не является процедурой обновления. Восстановление означает
возврат исходного полного bundle из доверенной копии, без новых credentials.

## Что не требуется внедрять сейчас

| Идея | Когда вернуться | Почему пока достаточно текущей схемы |
|---|---|---|
| Разные transport ingress и Internet exit для managed VPS | Повторяемая блокировка IP транспорта или явно усиленная модель угроз | Второй hop добавляет доверие, задержку, стоимость и отдельный отказ; home-first уже отделяет клиентский первый hop от VPS |
| WARP, дополнительные каскады, тотальная смена протокола | Измеренная проблема, которую кандидат устраняет на реальном приложении | Сам факт существования другого транспорта не даёт улучшения |
| Все устройства/сайты через VPS | Явная потребность конкретного устройства | Уже есть selected full-VPS; общая миграция затронет direct-сервисы и географию |
| Автоматический failover | Неприемлемое время ручного восстановления и готовая квалификация резервного egress | Работает ручной выбор роли; смена выхода меняет identity и требует отдельного проекта |
| DNS-география ради красивого checker | Воспроизведённая несовместимость или утечка | Страна resolver сама по себе не доказывает выход DNS к оператору |
| Автозапуск Amn / объявление lab production | Потребность в постоянной эксплуатации и готовность принять lifecycle ownership | Ручной lab сохраняет отдельные процессы, правила и восстановление |

[Статья Habr](https://habr.com/ru/articles/1103460/) и
[обсуждение](https://habr.com/ru/articles/1103460/comments/) дают гипотезы для
проверки. Причинная связь между российскими приложениями и блокировкой конкретных
foreign IP не установлена нашим аудитом. Это не основание усложнять рабочую схему.

## Порядок работы и закрытия

1. Закрыть RA-01 без изменения роутера; уточнить независимое восстановление пароля.
2. Завершить RA-03 и подготовить конкретный переход RA-02 для используемых клиентов.
3. После одобрения RA-02 выполнить переход по одному клиенту с rollback.
4. Отдельными окнами рассмотреть RA-04 и RA-05; RA-06 начинать с наблюдений.
5. RA-07/RA-09 запускать только по фактической потребности; RA-08 — после успешной
   ручной процедуры, чтобы автоматизировать уже проверенный процесс.
6. RA-10 восстановить до следующей runtime-поставки; RA-11 разобрать параллельно
   с ближайшими P1 и повысить приоритет исправления при подтверждённой применимости.

Для закрытия каждого ID нужны: реализованный механизм (если нужен), релевантные
локальные тесты, обновлённый runbook, приватное эксплуатационное доказательство и
rollback. Дата, версия и реальные результаты остаются в приватном журнале;
в публичном реестре фиксируется только безопасное обобщение статуса.
Commit/push сохраняет документацию, но не является deploy или клиентской приёмкой.

Широкие продуктовые идеи и Console follow-up остаются в
[общем backlog](future-improvements-backlog.md) и
[Console roadmap](ghostroute-console-post-mvp-roadmap.md). Этот документ — основной
реестр именно routing/privacy/recovery долгов, без дублирования их списков.
